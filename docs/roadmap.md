## 1. 产品目标与目标用户

Gaoming 的目标是让用户以较低的接入和维护成本，持续掌握主机与服务是否正常，在异常发生时及时收到提醒，并根据历史数据完成排查。

建议先围绕以下三类用户验证需求：

| 用户 | 典型场景 | 最需要的结果 |
| --- | --- | --- |
| 个人主机持有者 / 开发者 | 管理几台服务器，偶尔通过手机查看 | 快速接入、看懂状态、异常时收到提醒 |
| 小团队运维 / 值班人员 | 巡检多台主机，排查资源或服务异常 | 优先找到异常、定位原因、回看趋势、减少重复通知 |
| 团队管理员 | 分配权限、管理接入与维护活动 | 明确谁能看、谁能改，安全添加和移除主机，追踪操作 |

优先完整支持“接入一台主机 → 看见可信状态 → 收到异常提醒 → 找到原因 → 确认恢复”的流程。团队协作和规模能力在这条流程基础上扩展。

## 2. 当前体验与产品缺口

| 用户任务 | 当前已有体验 | 需要改善的地方 |
| --- | --- | --- |
| 第一次使用 | 有跨平台安装脚本；Agent 首次上报后自动出现在看板 | 缺少产品内接入向导、接入进度、失败排查和可用登录入口；无主机时主要显示“等待 Agent 上报” |
| 日常巡检 | 主机数量/状态摘要、CPU/内存概览、名称/IP/UID 搜索、主机卡片 | 缺少状态与分组筛选、异常优先排序、紧凑列表和常用视图；现有排序将离线主机放在在线主机之后 |
| 理解主机状况 | 有基础指标、动态指标分类、采集器状态和最近采样时间 | 指标多以原始名称展示；状态使用 UP/OFFLINE 等编码；缺测、过期、失败和正常零值需要更清楚地解释 |
| 相信实时数据 | 有实时连接提示、刷新入口和最近同步时间 | 连接状态需要与数据新鲜度区分；中断时应明确展示保留的旧数据，恢复后可靠同步，刷新失败提供反馈 |
| 查看变化 | 有 1m/5m/15m/1h 趋势选项 | 服务端摘要历史实际最多 60 点，不能把所选范围视为完整历史；动态指标仅保存最新快照，无法做长期回看 |
| 发现并处理异常 | 有状态字段和告警确认接口基础 | 没有完整告警规则、通知、告警列表、恢复和维护窗体验；页面存在“需要关注”统计不代表已能生成告警 |
| 判断服务可用性 | probe-worker 能探测固定 HTTP 地址 | 结果仅被接收和计数；没有用户配置目标、查看结果、关联主机或收到服务异常提醒的流程 |
| 团队使用 | 有用户管理页、角色/启用状态编辑及已有会话解析 | 登录页仍是占位；邀请成员、共享范围、操作记录和主机生命周期管理尚未完整提供 |
| 手机查看 | 现有页面有部分移动布局处理 | 独立移动/PWA 路由尚未接入；小屏浏览、图表交互、安装和更新流程需要验收 |

现状依据：[Dashboard](../web/src/pc/pages/PcDashboardPage.tsx)、[页面壳层](../web/src/pc/pages/PcShell.tsx)、[实时数据](../web/src/shared/features/hosts/useLiveHostsData.ts)、[路由](../web/src/app/router.tsx)、[用户页](../web/src/pc/pages/UsersPage.tsx)、[历史窗口装配](../server/internal/master/module.go)、[接入处理](../server/internal/ingest/service/service.go)。

## 3. 用户旅程与产品优先顺序

```mermaid
flowchart LR
    A[首次访问与接入] --> B[日常巡检]
    B --> C[发现异常与收到提醒]
    C --> D[判断主机或服务问题]
    D --> E[回看历史与处理]
    E --> F[确认恢复与团队交接]
    F --> B
```

| 安排 | 产品重点 | 用户价值 |
| --- | --- | --- |
| 近期 | M0 接入与安全访问、M1 可信看板 | 用户能开始使用，并准确理解当前状态 |
| 随后 | M2 告警处置、M3 服务可用性 | 用户无需持续盯屏，也能发现并处理问题 |
| 后续 | M4 历史分析与团队管理 | 支持复盘、比较和持续运营 |
| 按需求推进 | M5 移动/PWA 与扩展 | 方便离开电脑时查看，并适配实际使用规模 |

基础小屏可用性、可读性、错误反馈和权限提示贯穿所有阶段；PWA 安装等独立能力放在 M5。工程 TODO 的 P0 安全事项是私有多租户发布条件；P1 可靠性工作支撑看板和告警。产品优先顺序与工程优先级分别描述用户价值与实施约束。

## 4. 分阶段功能规划

### M0：顺利开始使用，并接入第一台主机

**用户目标**：第一次打开 Gaoming，就知道如何获得访问权限、添加主机，以及接入失败时怎么办。

**功能与体验**：

- 提供可用的登录和初始管理员流程；清楚区分个人/团队空间、演示与受限分享入口，说明当前查看范围。
- 无主机时展示“添加第一台主机”入口，按 Linux、macOS、Windows 提供安装引导、前置条件、复制操作和对应帮助。
- 安装信息绑定当前空间；凭据使用受限、安全的接入流程，并提示其有效期与撤销方式。
- 接入状态覆盖“尚未上报、已接入、接入失败”；首次上报后可直接打开该主机。无法观察安装进度时不显示推测进度。
- 接入失败按权限、网络、凭据、配置等原因提供下一步操作；重装/更新/卸载行为和对数据的影响可理解。
- 提供登录过期、无权限和分享失效的专用状态，避免让用户误以为“没有主机”。

**体验验收**：

- 在后端已可用、网络正常的环境中，首次使用者能仅按页面指引完成接入，不需要查找仓库内部配置说明。
- 无数据、无权限和接入失败分别展示不同状态，每种状态都有明确下一步。
- 主机接入正确空间；分享和安装凭据可撤销，私有数据不因知道空间编码即可被访问。

工程关联：P0-01～P0-07、P1-10。接入向导、进度和失败引导是本次新增的产品要求，实施前需补充到工程任务。

### M1：一眼找到异常，并看懂可信的实时数据

**用户目标**：打开总览后快速判断哪些主机需要关注，进入详情时知道数据是否新鲜、异常发生在哪里。

**功能与体验**：

- 总览突出异常、离线和数据过期数量；点击摘要直接进入对应筛选结果。正常主机概览保持简洁。
- 在现有搜索基础上增加状态筛选与排序，支持异常优先、名称和资源使用量排序；按主机数量提供卡片或紧凑列表。
- 主机详情使用可分享的站内地址，恢复浏览器前进/后退与筛选条件；从告警或通知进入时能定位对应主机和指标。
- 指标展示中文/可读名称、单位与必要解释；常用指标优先，文件系统、网卡、设备等详细维度按需展开。
- 将“正常零值、未采集、不支持、采集失败、数据过期”区分展示；过期指标不能继续表现为当前健康数据。
- 区分“实时连接正常”和“主机仍在上报”；展示主机最后采样时间，断线时保留旧数据并标注，重连后恢复一致状态。
- 趋势图标出实际可用范围、缺口与采样间隔；没有足够历史时直接说明，不用补零制造完整曲线。
- 加载、空列表、搜索无结果、刷新失败和详情读取失败有独立反馈与重试入口；平均资源统计说明样本范围，排除不适用的过期/缺测样本。

**体验验收**：

- 用户可从“离线”或“需要关注”摘要直接定位主机，不必逐张卡片检查；异常排序和状态含义一致。
- 停止 Agent、断开页面实时连接、让采集器失败，界面能分别解释这些情况；恢复后不残留错误状态。
- 切换空间、刷新、返回和打开详情链接不会带入其他空间数据，也不会无故丢失当前浏览上下文。
- 选择 1h 时，用户能辨别实际只有短期数据；缺测不被解释为资源使用量为零。

工程关联：P1-01～P1-05、P1-08、P1-11，依赖 M0 的访问规则。筛选、排序、列表、详情路由和指标解释是需要补充的产品任务；CI、迁移和公共仓储整理可同步推进。

### M2：不盯屏也能收到提醒，并完成告警处置

**用户目标**：知道发生了什么、影响哪台主机、是否需要处理，以及何时已经恢复。

**功能与体验**：

- 先提供离线、CPU、内存和磁盘规则模板；配置界面说明阈值、持续时间与恢复条件，允许按实际需求调整。
- 告警列表区分待处理、已确认与已恢复，支持严重性/主机/时间筛选；详情说明触发条件、实际值、开始时间、影响对象和状态原因。
- 接通至少一种通知渠道，提供测试发送、发送失败反馈和通知历史；消息附带可授权访问的告警详情链接。
- 确认告警表示“有人接手”，恢复表示“异常条件解除”；界面解释两者区别，避免确认后误认为问题已解决。
- 维护窗可创建、查看、修改与停用，说明作用对象、起止时间和将抑制哪些提醒；维护结束自动恢复约定行为。
- 同一持续异常合并为一个活动告警；配置恢复提醒与必要的重复提醒频率，降低通知噪声。

**体验验收**：

- 从模拟异常、收到通知、打开详情、确认到自动恢复，可以完成完整流程，通知失败可被发现和重试。
- 同一异常持续期间不反复生成新告警；数据缺测不伪装成正常值，维护期间按设置抑制提醒。
- 用户能回答“谁在处理、是否恢复、为什么触发”，操作者和时间有记录。

工程关联：P2-01～P2-04；依赖可信采样与状态、租户授权、持久化和通知恢复机制。按主机或告警场景实现必要依赖后交付，不要求先完成所有无关工程整理。

### M3：从主机健康延伸到服务是否可用

**用户目标**：除了知道服务器在上报，还能知道其网站或 HTTP 服务是否正常响应。

**功能与体验**：

- 提供 HTTP/HTTPS 探测目标管理，配置地址、间隔、超时与期望响应；支持启停和手动验证配置。
- 展示最近探测时间、响应状态、延迟、失败原因和短期趋势；区分超时、连接失败、响应不符合预期与未执行探测。
- 将服务关联主机或分组，让详情分别展示 Agent 上报状态与服务探测状态，并说明总状态的来源。
- 接入 M2 告警规则与通知，用户能从服务异常跳转到目标和关联主机，查看相近时间的资源变化。
- 在事件时间线中记录已支持的 Agent、服务与状态变化，方便判断故障发生顺序。
- 配置私有网络目标时说明授权与探测范围；探测配置错误和任务未执行不能显示为服务正常。

**体验验收**：

- 用户可完成添加目标、验证、持续探测、收到失败提醒、查看原因和确认恢复的流程。
- “Agent 未上报但服务可访问”与“Agent 正常但服务异常”有不同且易理解的展示。
- 对未授权探测目标给出可操作的拒绝提示，无法绕过访问限制。

工程关联：P2-05～P2-07；状态和告警联动依赖 M2。未来的 DNS、TCP、证书检查、多地点探测按需求另行评估，本阶段先交付完整 HTTP/HTTPS 场景。

### M4：回看问题，管理主机，并与团队协作

**用户目标**：比较故障前后的指标，整理主机，并把异常、维护和处理记录交接给同事。

**功能与体验**：

- 基于真实保留能力逐步开放 24h、7d 等历史范围与自定义时间；按主机、指标和维度筛选，支持统一时间轴对照资源、告警、探测和事件。
- 标注历史精度、聚合方式、缺口和保留期限；先提供基础摘要历史，再开放按设备/挂载点/网卡查询的动态指标历史。
- 提供分组与标签管理、组合筛选和保存常用视图；可读主机名称与稳定身份分开显示。
- 管理 Agent 版本、上报间隔与接入状态；配置修改显示生效结果，失败时有恢复路径。
- 主机停用、删除和撤销接入明确区分；确认界面说明历史保留、告警影响及后续上报行为。
- 提供成员邀请/加入、管理员和成员权限说明、撤销访问以及操作记录；先沿用可维护的基础角色模型，细粒度权限按需求扩展。
- 允许分享受限主机/视图或排查上下文，明确分享内容、有效期与撤销入口；接收方仍须满足访问规则。

**体验验收**：

- 用户从一条告警进入其发生时段，能在同一时间范围查看主机和服务变化，辨别缺测及精度差异。
- 添加/移除成员、改权限、创建维护窗和删除主机都能说明结果与影响，越权操作被拒绝。
- 常用视图可恢复；共享链接不泄露额外字段；成员离开或链接撤销后不能继续访问。

工程关联：P2-08～P2-10、P0-01～P0-03。成员邀请、保存视图、关联时间轴及分享管理需新增工程任务。基础成员访问随 M0 完成；历史与运营能力可按独立场景逐步交付。

### M5：离开电脑也能查看，并按需求扩展

**用户目标**：在手机上快速查看告警和关键主机，方便返回同一工作空间，同时维持一致、可理解的体验。

**功能与体验**：

- 移动首页优先呈现异常、离线与告警，支持从通知打开对应详情；筛选、主机详情和告警确认可单手完成。
- 图表支持适合触屏的读数和时间范围切换；详细指标按需展开，避免长表格成为默认入口。
- 在支持环境提供 PWA 安装与版本更新提示，解释离线可查看范围和最后更新时间；私有历史缓存按权限与退出规则清理。
- 深浅色和现代/Pixel 外观保持状态、单位、布局层次与交互一致；键盘、触屏与辅助阅读均可操作。
- 按真实主机规模与使用频率优化页面和实时连接，保证主机数量增加后仍易于筛选与定位。
- Agent 升级提供版本、影响和失败回退说明；进程监控等新增采集能力须先验证需求，显式启用并说明数据范围。

**体验验收**：

- 主流目标手机尺寸可完成查看异常、筛选、打开详情和确认告警，无必须依赖悬停的操作；无需整页横向滚动才能完成核心任务。
- 安装、升级、离线再上线和退出流程可验证；离线数据不能呈现为实时状态，也不能跨账号残留。
- 两种外观中的异常状态都可由文字/图标辨认；移动告警入口复用已有通知渠道，浏览器推送另行评估。

工程关联：P3-01～P3-05。可在 M1 同步改善现有响应式页面；PWA、受控升级和可选采集依据用户反馈与容量结果单独排期。

## 5. 跨阶段体验规则

| 场景 | 产品规则 |
| --- | --- |
| 状态与信息层次 | 用中文状态、原因和更新时间解释健康状况；总览展示关键结论，详细维度在详情按需展开 |
| 数据可信度 | 展示实际采样时间与可用范围；区分未知、缺测、过期和零值；连接成功不等于主机数据新鲜 |
| 加载与错误 | 区分首次加载、后台刷新、无数据、无权限、请求失败和断线；可重试操作提供入口，说明保留数据是否过期 |
| 操作反馈 | 保存、确认、刷新、启停均显示处理中与结果；失败保留输入；有影响的操作说明范围，避免用户重复提交 |
| 导航与上下文 | 主机/告警详情有可授权访问的链接；浏览器返回、刷新、空间切换和通知跳转保留正确上下文 |
| 可访问性 | 状态不能只靠颜色；常用动作可键盘操作，焦点可见，图表与数值单位可理解；复用现有[现代规范](../web/DESIGN_SYSTEM.md)和[Pixel 规范](../web/PIXEL_DESIGN_SYSTEM.md) |
| 安全与权限 | 在查看、分享、接入和删除时说明数据范围与影响；后台验证所有权限，隐藏按钮不能替代授权 |
| 长期维护 | 每次更新说明新增能力、实际支持平台、历史保留与升级影响；页面能力与文档描述保持一致 |

## 6. 建议首轮产品交付

首轮完成 M0 的可用登录、安全接入和新用户引导，以及 M1 的异常定位与数据可信度提示。形成可发布的最小使用流程：

1. 首次用户进入正确空间，获得明确的访问与接入指引。
2. 安装 Agent 后看见主机，失败时知道下一步如何排查。
3. 在总览按异常或离线筛选，打开可读的主机详情。
4. 在停止上报、页面断线或采集失败时，看见正确原因与时间。
5. 恢复后自动同步，分享与退出流程遵守权限边界。

随后交付 M2 的“异常通知 → 告警详情 → 接手 → 恢复”流程，再扩展服务探测。首轮筛选与详情设计应为告警跳转预留一致入口。长期历史、团队运营和 PWA 根据验证结果分阶段加入。

## 7. 产品验证与衡量

先用三类目标用户的真实任务建立基线，再设定目标。以下是建议观察口径，不是已达成指标；是否采集产品事件及其隐私策略需在实施前确定。

| 目标 | 衡量方式 | 验证方法 |
| --- | --- | --- |
| 降低接入门槛 | 首次接入完成率、接入耗时、失败原因和求助次数 | 在后端已可用环境，观察首次用户从打开接入页到主机可见；区分安装前置问题与产品流程问题 |
| 更快找到异常 | 正确定位目标主机的完成率、耗时和操作次数 | 给出“找到离线主机”“找到内存异常主机”等任务，观察筛选和详情使用 |
| 看懂数据 | 能否正确区分离线、断线、缺测、过期与正常零值 | 对各类状态做情景验证，检查用户判断与下一步操作 |
| 提醒有用且可控 | 触发到通知耗时、发送成功率、重复/误报比例、接手耗时 | 在规则条件满足后计时，模拟持续异常、恢复、维护窗和通知失败 |
| 排查与复盘有效 | 能否定位触发指标与发生时段，是否找到恢复证据 | 从告警进入历史与服务详情，完成故障前后对照 |
| 手机能完成核心任务 | 核心任务完成率、误触与不可操作控件数量 | 在选定设备尺寸验证查看、筛选、详情、确认和返回 |

结合任务观察、失败原因和访谈调整优先级。页面访问量或新增主机数不能单独证明产品流程可用；后台的延迟、写入一致性和恢复验证仍按工程 TODO 执行。

## 8. 工程衔接与安全检查

Roadmap 以用户结果组织；工程 TODO 保留身份、授权、可靠性、数据与部署的实施约束。新提出的体验需求在排期时应拆成页面/流程任务，补充到 TODO 或 Issue，并标注所属 M 阶段、依赖与验收场景；本文更新不表示相关能力已实现。

发布前按功能核对权限与资源边界：私有访问和接入凭据随 M0 验收，可信状态和异常恢复随 M1 验收，通知出站目标随 M2 验收，探测 SSRF 防护随 M3 验收，历史配额与分享范围随 M4 验收，私有缓存和升级来源随 M5 验收。SQL、配置与部署变更按仓库规范同步升级文档和回滚路径。

本次仅更新 roadmap 文档，没有新增运行时代码或凭据。既有匿名读取、Agent/worker 鉴权缺口和运维租户绑定问题仍是 P0 风险，不能为了简化接入或分享而跳过修复。新增采集继续遵守[采集安全边界](./agent-adaptive-collection.md)，不默认上传进程命令行、环境变量或连接明细。
